# Epic 3 — Demo Manifests and End-to-End Approval Demo

## Context

The Kubernetes MCP Guard project's value — approval-gated AI-assisted Kubernetes ops — is hard to grasp from prose alone. Today the repo has all the parts (14 MCP tools, plan/apply approval flow, JSONL audit, RBAC, kubeconfig generator, local OAuth), but no concrete narrative that walks a reader through *seeing* the safety model work end-to-end.

Epic 3 fixes this by adding (a) two small demo manifests under `examples/failing-deployment/` so the existing quickstart has something to run against, and (b) a step-by-step doc at `docs/demo-failing-deployment.md` that exercises read-only diagnosis, mutation proposal, approval, apply, verification, and audit inspection. The demo must reuse existing tools and scripts rather than invent new conventions.

This implements **Epic 3** of [.agents/Plans/roadmap-final.md](../../MyRepos/GitRepos/k8s-toolkit/.agents/Plans/roadmap-final.md). It is split per the roadmap's phasing: Phase 1 lands the manifests so the Phase 1 quickstart can demo against something real; Phase 2 lands the narrated walkthrough.

## Phase

- **Phase 1 portion** (manifests only): `examples/failing-deployment/{deployment.yaml,fix.yaml}`. Low risk, immediately useful to the Epic 2 quickstart.
- **Phase 2 portion** (narrated demo): `docs/demo-failing-deployment.md` plus README link.

This plan covers both portions in one document; an implementer can land them as two separate PRs if preferred.

## Step 1 — Add `examples/failing-deployment/deployment.yaml` (broken workload)

**Goal:** a Deployment that visibly fails in a way the read-only diagnostic tools surface cleanly, but is fixable through one small mutation plan.

**Failure mode (recommendation):** wrong container image tag.

- `image: nginx:1.27-doesnotexist` → produces `ImagePullBackOff` / `ErrImagePull` Pod status, `Failed` events, no logs (intentional — demonstrates `get_pod_diagnostics` showing container state, and `get_k8s_events` showing the puller's error).
- The fix in Step 2 is `image: nginx:1.27-alpine` (a real published tag), applied via `request_set_deployment_image` — the cleanest tool to demo without typing manifest YAML twice.

Avoid these failure modes:
- **Bad readiness probe** — fixing it requires re-applying the manifest, which makes the demo feel like a `kubectl apply` retry rather than a deliberate mutation plan.
- **Resource limits too tight** — flaky on minikube depending on host RAM; non-deterministic.
- **CrashLoopBackOff via bad command** — produces logs, but Pod restart timing makes the "diagnose with `get_pod_logs`" beat slow and racy.

ImagePullBackOff is the most teachable failure: deterministic, fast, surfaces in Events + Pod conditions but not logs (good narrative — "we tried logs, no logs because the container never started, so we look at events").

**Manifest shape:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-demo
  namespace: mcp-nginx-demo
  labels:
    app.kubernetes.io/name: nginx-demo
    app.kubernetes.io/managed-by: infra-gate-mcp
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: nginx-demo
  template:
    metadata:
      labels:
        app.kubernetes.io/name: nginx-demo
    spec:
      containers:
        - name: nginx
          image: nginx:1.27-doesnotexist   # intentionally broken — fixed by request_set_deployment_image
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: 10m
              memory: 32Mi
            limits:
              cpu: 100m
              memory: 64Mi
---
apiVersion: v1
kind: Service
metadata:
  name: nginx-demo
  namespace: mcp-nginx-demo
  labels:
    app.kubernetes.io/name: nginx-demo
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: nginx-demo
  ports:
    - port: 80
      targetPort: 80
```

**Discipline:**
- Single multi-document YAML so `kubectl apply -f deployment.yaml` works without scripting.
- `metadata.namespace: mcp-nginx-demo` on every resource — `K8sManifestParser` rejects manifests whose namespace conflicts with the tool namespace.
- `replicas: 2` so `get_k8s_status` shows `desired=2, ready=0, available=0` (drama).
- Modest resource requests — works on a default minikube.
- Container name `nginx` so the Step-2 `request_set_deployment_image` call has a stable container reference.

**A note on bootstrap.** The Deployment is intentionally broken, so the user is expected to apply it with `kubectl apply -f` (not via the gateway) before the demo begins. The demo doc must call this out — applying via the gateway would just produce a plan for a known-broken object, which is a confusing first step.

## Step 2 — Add `examples/failing-deployment/fix.yaml` (reference fix)

**Goal:** show what a "good" Deployment looks like for readers who skim the manifests, and provide a fallback for readers using `request_apply_manifest` instead of `request_set_deployment_image`.

**Manifest:** identical to Step 1 except `image: nginx:1.27-alpine`. Same name, namespace, labels, replicas, ports, resources, and the same Service. The demo's primary path uses `request_set_deployment_image`; `fix.yaml` is documented as the alternate path for readers who want to demo the manifest-apply flow.

**Discipline:** keep the diff between `deployment.yaml` and `fix.yaml` to the single line that matters (the image tag). A reader who runs `diff deployment.yaml fix.yaml` should see exactly the bug.

## Step 4 — Add `docs/demo-failing-deployment.md` (narrated walkthrough) — Phase 2

**File:** `docs/demo-failing-deployment.md` (new). Single owner per the doc-ownership table. Do not move OAuth, security, env-var, or architecture content into this doc — link instead.

**Audience:** a reader who has the gateway running per Mode C (Option 1 or Option 2 from README) and wants to see the safety model in action. The doc must work for both Codex CLI users (MCP elicitation path) and users without elicitation (`scripts/approve-plan.sh` path).

**Required sections, in order:**

1. **What this demonstrates** (3–5 sentences) — read-only diagnosis, mutation proposal, hash-bound approval, exact-plan apply, verification, audit. State that this is the safety model in action; production-grade controls are documented in Epic 4's [docs/security-model.md] (forward link, even before that doc exists — it lands in Epic 4).

2. **Prerequisites** — bullet list with links, no new instructions:
   - Gateway running (link to README "How To Run", Option 1 or Option 2).
   - `./scripts/create-demo-kubeconfig.sh --compose` already run.
   - An MCP client connected — Codex CLI per README, or any MCP client supporting elicitation. Note the `scripts/approve-plan.sh` fallback for clients without elicitation.
   - `kubectl` available locally (only needed to apply the broken manifest in Step 1).

3. **Step 1 — Deploy the broken workload** — `kubectl apply -f examples/failing-deployment/deployment.yaml -n mcp-nginx-demo`. One sentence explaining why this uses kubectl (the workload is intentionally broken; the gateway is for the *fix*).

4. **Step 2 — Inspect with read-only tools** — show three calls and what each surfaces:
   - `get_k8s_status` with `namespace=mcp-nginx-demo` → `nginx-demo` Deployment, `desired=2 ready=0 available=0`, two Pods in `ImagePullBackOff`.
   - `get_k8s_events` with `namespace=mcp-nginx-demo` → "Failed to pull image" / "Back-off pulling image" events.
   - `get_pod_diagnostics` with one of the failing Pod names → container state `waiting: ImagePullBackOff`, no logs.
   - One paragraph noting `get_pod_logs` returns empty (container never started) — that empty result is itself a diagnostic signal.

5. **Step 3 — Propose the fix (mutation plan)** — primary path with `request_set_deployment_image(namespace=mcp-nginx-demo, name=nginx-demo, container=nginx, image=nginx:1.27-alpine)`. Show the returned `PlanId` and the plan summary. State that nothing has been applied yet.
   - Subsection "Alternate: `request_apply_manifest`" — short paragraph showing the same fix can be planned by submitting `examples/failing-deployment/fix.yaml`. One sentence on when to prefer which (`set_deployment_image` for narrow image swaps, `apply_manifest` for broader changes).

6. **Step 4 — Approve the plan** — two subsections:
   - **Codex CLI / elicitation path**: `apply_approved_plan(planId=…)`; user gets an elicitation prompt; approving triggers the apply.
   - **`scripts/approve-plan.sh` fallback**: `./scripts/approve-plan.sh <plan-id>` writes `.mcp-approvals/approved/<plan-id>.sha256`; `apply_approved_plan(planId=…)` then succeeds without elicitation. State this is for MCP clients that do not support elicitation; it is **not** a way to bypass approval — the file-system action is the approval.

7. **Step 5 — Apply** — `apply_approved_plan(planId=…)` returns the apply result. Note that any tampering with the pending plan between approval and apply changes the hash and trips `approval_hash_mismatch` (audited, refused).

8. **Step 6 — Verify recovery** — re-run `get_k8s_status` and `get_pod_diagnostics`; expect `ready=2 available=2`, Pods `Running`. Optional: `get_pod_logs` now returns nginx access log lines.

9. **Step 7 — Inspect the audit** — point readers at:
   - `.mcp-approvals/audit.jsonl` (server-side: `plan_requested`, `plan_approved`, `plan_applied`).
   - `.mcp-guardrails/audit.jsonl` (gateway-side: tool calls with subject identity, action `warn` or `audit`, redaction info).
   - One JSONL example for each; do not duplicate full schemas (they live in the source files).

10. **Step 8 — Cleanup** — `kubectl delete -f examples/failing-deployment/deployment.yaml -n mcp-nginx-demo`. Note that the gateway-mediated equivalent is `request_delete_manifest` followed by `apply_approved_plan`; the demo shows `kubectl` here for symmetry with Step 1.

11. **Troubleshooting** (short) — three rows:
    - Plan not found: ensure the gateway and server share the same `K8S_MCP_APPROVAL_ROOT` (the compose mount handles this).
    - `approval_hash_mismatch`: do not edit the pending plan JSON between approval and apply.
    - Codex elicitation prompt does not appear: client may not support elicitation; use `scripts/approve-plan.sh`.

**Discipline:**
- No new env vars, no new endpoints, no new namespaces. Use only what's already wired.
- Do not duplicate `docs/setup-guide.md` setup steps. Link.
- Do not describe guardrails as the primary safety boundary — that framing belongs to Epic 4. This doc is operational; the security argument is referenced, not restated.
- Use real tool names with the snake_case shape they ship in (`get_k8s_status`, not `getK8sStatus`).
- For each step, include a one-line "what you should see" expectation so a reader can self-verify.

## Verification (end-to-end)

Manual verification on a clean checkout, gateway running per README Option 1:

1. **Manifests parse-clean.** `kubectl apply --dry-run=server -f examples/failing-deployment/deployment.yaml -n mcp-nginx-demo` succeeds. Same for `fix.yaml`.
2. **Broken state is reproducible.** After `kubectl apply -f examples/failing-deployment/deployment.yaml`, within ~30 seconds `kubectl get pods -n mcp-nginx-demo` shows two Pods in `ImagePullBackOff`.
3. **Read-only tools surface the failure.** Calling `get_k8s_status`, `get_k8s_events`, and `get_pod_diagnostics` from an MCP client returns the failure shape described in the doc (container state `waiting: ImagePullBackOff`, "Failed to pull image" event, empty logs).
4. **Plan creation works.** `request_set_deployment_image(namespace=mcp-nginx-demo, name=nginx-demo, container=nginx, image=nginx:1.27-alpine)` returns a `PlanId` and the corresponding `.mcp-approvals/pending/<id>.json` file exists.
5. **Approval works both ways.**
   - With Codex elicitation: `apply_approved_plan` prompts; approving applies; Pods recover to `ready=2`.
   - With `scripts/approve-plan.sh <plan-id>`: an `.mcp-approvals/approved/<id>.sha256` file appears with a non-empty hash; subsequent `apply_approved_plan` succeeds without prompting.
6. **Tamper detection works.** Editing `pending/<id>.json` between approval and apply produces an `approval_hash_mismatch` audit entry and the apply is refused. (Optional sanity check; document the expectation, do not require this in the demo doc itself.)
7. **Audit shows the full flow.** `.mcp-approvals/audit.jsonl` contains `plan_requested`, `plan_approved`, `plan_applied` for the same `planId`. `.mcp-guardrails/audit.jsonl` contains entries for each tool call with subject identity.
8. **Recovery is visible.** `get_k8s_status` after apply shows `ready=2 available=2`.
9. **Cleanup is clean.** `kubectl delete -f examples/failing-deployment/deployment.yaml` removes Deployment and Service; `get_k8s_status` shows nothing in `mcp-nginx-demo`.
10. **Doc renders cleanly.** README link to `docs/demo-failing-deployment.md` resolves; demo doc internal anchors resolve; no broken Markdown.
11. **Scope discipline.** `git status` shows no edits outside the deliverables list above.
