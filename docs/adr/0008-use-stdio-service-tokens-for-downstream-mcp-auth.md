# Use Stdio Service Tokens For Downstream MCP Auth

InfraGate will keep the McpServer as a private stdio downstream process and authenticate Gateway-to-server calls with a Gateway Service Identity token issued by the configured OAuth/OIDC provider, starting with the existing Keycloak realm. The Gateway obtains a short-lived client-credentials access token, audience-restricted to the downstream MCP server, and attaches it to each downstream MCP request in a private `_meta` field; the McpServer requires that token for all downstream requests, including discovery, and validates issuer, signature, lifetime, audience, `mcp:downstream` scope, and configured gateway client identity.

The fully standard MCP/OAuth shape would expose the downstream server as an HTTP protected resource and rely on bearer-over-TLS semantics, protected-resource metadata, and conventional OAuth middleware. That aligns better with the MCP Authorization specification and OAuth bearer-token RFCs, but it also creates a new network-addressable component. Keeping stdio preserves the current smaller attack surface, but token presentation over MCP `_meta` is an InfraGate-private convention and is not encrypted by OAuth itself; secrecy relies on process/container isolation, launching the trusted server binary directly, short token lifetime, strict audience/scope checks, and redaction of the private `_meta` token field from logs, audit events, traces, and exception text.

Production deployments fail closed when downstream auth is not configured. Direct unauthenticated stdio remains available only through an explicit development/test opt-out. The Gateway caches the service token in memory, refreshes before expiry, retries once after an expired/invalid downstream-auth rejection, and then returns a clear auth failure without logging the token. Future hardening options include moving the downstream boundary to the standard MCP HTTP auth model, sender-constrained tokens such as mTLS or DPoP where transport supports them, request signing or challenge-response over stdio, and stronger runtime isolation for same-host process threats.
