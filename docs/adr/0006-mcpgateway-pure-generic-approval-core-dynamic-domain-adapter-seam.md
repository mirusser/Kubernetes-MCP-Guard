# Make McpGateway a Pure Generic Approval Core With a Dynamic Domain Adapter Seam

The McpGateway currently violates ADR 0001 by holding direct Kubernetes domain knowledge: it statically declares K8s MCP tool stubs (`K8sGatewayTools`), embeds K8s tool names in its conventions, and references `InfraGate.KubernetesAdapter` to wire `KubernetesPlanReviewAdapter` and `KubernetesPlanReviewRenderer`. This couples the Generic Approval Core to the Kubernetes Adapter in exactly the way ADR 0001 intended to prevent.

InfraGate will make McpGateway a pure Generic Approval Core by replacing the static K8s tool layer with dynamic tool discovery. The gateway discovers the downstream Domain Adapter's tool list at startup via the MCP protocol, forwards `ReadOnly` tools as-is with guardrails, suppresses `Destructive = true` tools from the AI, and generates corresponding `request_[tool]` wrapper tools that create Plan Envelopes via an `IDomainPlanBuilder` seam defined in `InfraGate.Approvals`. The static `apply_approved_plan` tool remains Gateway-owned: after the generic Pre-Execution Gates pass, execution delegates to an `IDomainPlanExecutor` seam (also in `InfraGate.Approvals`) that owns domain-specific Freshness Checks and Domain Policy Checks before calling the downstream executor. Both seams receive an `IToolCaller` (also in `InfraGate.Approvals`) to call downstream MCP tools, implemented by the existing `DownstreamMcpClient` in the Gateway process.

The McpServer is restructured to expose ReadOnly evidence tools (dry-run, diff) and raw `Destructive = true` execution tools, removing all plan and approval vocabulary (`Request*`, `ApplyApprovedPlan`, `requesterSubject` parameters). It becomes a trusted execution substrate addressed only by the Gateway process. The accepted trade-off is that the McpServer no longer independently validates Approval Grants before mutating, relying on deployment topology (McpServer reachable only by the Gateway) as the backstop. All gate checks — generic gates by the Gateway and domain-specific gates by `KubernetesPlanExecutor` — happen in the Gateway process before any execution call is issued.

## Considered Options

- **Static K8s tool stubs in a separate `InfraGate.McpGateway.Kubernetes` project** — rejected because the gateway host would still carry a project reference to `InfraGate.KubernetesAdapter`, preserving the coupling at the deployment-unit boundary even if the logical layer looked cleaner.
- **Dynamic tool mirroring without the `request_*` / `apply_approved_plan` split** — rejected because a fully transparent proxy cannot intercept mutations for approval gating or inject the authenticated requester identity into plan creation.
